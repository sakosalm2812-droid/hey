# Teacher answer-key access contract

HEY identifies an answer key from `content` fields named `teacherAnswer`, a student worksheet from `content.type === "teacher_worksheet"`, and a teacher lesson from its lesson content shape. The `audience` and other metadata do not grant access. The canonical HEY artifact read, list, version, history, comparison, and export paths require `supabaseClient.auth.getUser()` to return an authenticated user with server-managed `app_metadata` claims:

- `hey_role: "teacher"`
- `hey_account_scope: <the artifact metadata accountScope>`
- `hey_class_ids: [<the artifact metadata classId>, ...]`

Assessment creation and save also bind an explicit class ID to the active class context. HEY denies an answer key when the role, account, class, or authenticated user is missing or mismatched. A student may read a worksheet only with matching account and class claims; only a teacher may save or export it. Client-supplied context can narrow the check, but cannot establish identity or grant a role. Legacy assessment/lesson workflow or artifact-contract markers keep damaged records on their private authorization path even when content fields are incomplete. Private Teacher lessons and answer keys are readable only by their authenticated creator (`created_by` must equal the active Supabase user ID) in addition to matching account claims and any class scope on the artifact. New individual Teacher saves record the creator from `auth.getUser()`, and version/history checks retain the parent creator boundary. Missing creator identity fails closed for private lesson and answer-key reads. Student worksheets remain class-readable under their teacher/student role rules. The complete lesson journey builds all artifacts first, then persists the teacher lesson, teacher answer key, and student worksheet through one transaction-backed RPC. The RPC checks the signed role/account/class claims, common workspace/class/journey, and student worksheet content shape. It is idempotent for retries using the same journey ID and payload. After persistence, HEY verifies all three returned rows, including owner, workspace, account/class, and full content, before adding any to its local cache. If the response is lost or mismatched, the error contains the journey ID, stable artifact IDs, and timestamp needed to retry safely.

## Enforcement gap

This repository has no server-side claim provisioner or verified class-membership source, and no reviewed Supabase Row Level Security policy or table definition for `hey_artifacts` or `hey_artifact_versions`. The batch function requires each artifact's metadata workspace ID to match its routed project ID and checks that all three share that ID. This prevents inconsistent routing metadata, but there is no signed workspace-membership claim or canonical workspace-to-account relation available here to prove that ID belongs to the authenticated account. Do not treat workspace equality as tenant authorization. The contract therefore fails closed until an administrator or trusted server provisions the role/account/class claims, and workspace membership is independently bound. The new batch function is a migration only: it has not been applied or exercised against a configured Supabase database in this checkout. HEY protects reads, version data, and exports through its application API. A user who can query Supabase tables directly may bypass that application check unless database RLS independently denies unauthorized rows. That direct-database enforcement is not implemented or verified here, so application-path secrecy is not a claim of database-wide secrecy.
